WHAT THE SAS PROGRAM DOES
================================================================================

INPUTS:  4 CSV files
  └─ demographics.csv (subject info)
  └─ vitals.csv (vital signs measurements)
  └─ adverse_events.csv (reported adverse events)
  └─ lab_results.csv (lab test results)

PROCESS:
  ├─ Section 1: Import CSVs into SAS
  ├─ Section 2: Validate demographics (age, sex, dates, duplicates)
  ├─ Section 3: Validate vitals (ranges, missing, logic checks)
  ├─ Section 4: Validate adverse events (terms, severity, dates)
  ├─ Section 5: Validate lab results (values, units, ranges)
  ├─ Section 6: Generate data quality report (RTF)
  └─ Section 7: Generate clinical study report tables (RTF)

OUTPUTS: 2 RTF files
  └─ clinical_study_tables.rtf (CSR submission-ready)
  └─ data_quality_report.rtf (validation details)

================================================================================
VALIDATION RULES AT A GLANCE (26 TOTAL)
================================================================================

DEMOGRAPHICS (5 checks)
  1. Age present
  2. Age 18-100 years
  3. Sex = M or F
  4. Enrollment date present
  5. Subject ID unique (no duplicates)

VITAL SIGNS (12 checks)
  6-9. Missing value checks (Systolic, Diastolic, HR, Temp)
  10-13. Range checks (BP 70-250, 40-150; HR 30-220; Temp 34-42)
  14. BP logic (Diastolic < Systolic)
  15-16. Visit date present, not before enrollment
  [Note: WEIGHT_KG not validated as it's not critical vital sign]

ADVERSE EVENTS (5 checks)
  17. AE term present
  18. Start date present
  19. Severity present
  20. Severity value valid (MILD/MODERATE/SEVERE)
  21. End date >= Start date

LABORATORY RESULTS (4 checks)
  22. Result present
  23. Unit present
  24. Result is numeric (implicit)
  25-26. Reference range presence + auto-derivation (LOW/NORMAL/HIGH)

QUICK CUSTOMIZATION GUIDE
================================================================================

To run on YOUR data:

1. Update paths (line 11-13):
   %LET sourcepath = C:\your_data_folder;
   %LET sdtmpath   = C:\sdtm_output;
   %LET reportpath = C:\reports;

2. Update CSV file names if different (lines 24-45)
   DATAFILE="&sourcepath./YOUR_FILENAME.csv"

3. Update variable names if different (RENAME statements)
   Example: If your age column is "AGE_IN_YEARS" instead of "age":
   RENAME age=AGE → RENAME age_in_years=AGE

4. Customize validation ranges if needed (Sections 2-5)
   Example: Change age upper bound from 100 to 85:
   Find: IF NOT MISSING(AGE) AND (AGE < 18 OR AGE > 100)
   Replace: IF NOT MISSING(AGE) AND (AGE < 18 OR AGE > 85)

5. Run it:
   Submit the modified program to SAS
   Check SAS log for ERRORS (should be none)
   Verify output RTF files created

QUESTIONS YOU'LL GET IN INTERVIEWS
================================================================================

Q: "Why did you implement these specific validation rules?"
A: "Each rule addresses a real CDM challenge. Age ranges are based on enrollment 
   criteria and physiologic limits. BP logic catches common data entry errors 
   (transposed values). Missing value checks are mandatory. I chose the rules to 
   catch the 80/20 of common errors."

Q: "How would you handle 100 records with DQ issues?"
A: "I wouldn't exclude them. I'd report all 100 to the data coordinator with 
   the specific issue for each. They'd prioritize: critical issues (missing 
   severity) vs. investigational (outlier age). We'd create targeted queries 
   to sites, document resolution, and proceed with analysis."

Q: "What if some validation rules don't apply to a study?"
A: "I'd adjust them. If a study enrolled only ages 65+, I'd change the lower 
   bound from 18 to 65. If temperature wasn't collected, I'd remove that check. 
   The framework stays the same; the rules change per protocol."

Q: "Can this extend to other domains (DQ, EQ, MQ)?"
A: "Yes. The validation logic is identical for any domain. You create flags, 
   report issues, let data team investigate. I could add DOSING (EX) domain 
   with dose/frequency/route validation, or QUESTIONING (QS) for PRO scoring."

Q: "What's your approach to testing this program?"
A: "I'd run it on sample data with known issues. Deliberately create age=150, 
   diastolic>systolic, missing severity. Verify each gets flagged correctly. 
   Then run on clean data and confirm no false positives. Finally test on 
   actual study data and compare flagged records to manual review."
